### A3. P1：STOP、rotation 与 stopping identity 必须同时成立

当前 STOP 写 tombstone/receipt 后，`submit()` 先 rotation 再 stamp。rotation 删除全部 tombstone。
因此在 receipt threshold−1 时提交 STOP：

- 健康 teardown：post-rotation state 没有该 section，但 `committed` 仍保留 rotation 前 revision/epoch，
  新 strict codec 会拒绝本服务器自己的合法 200；
- teardown fault：内部仍保存 `stopping` id，但 authority tombstone 被 rotation 删除；GET 只遍历
  authority entries，于是仍活的 watch 从 desk 完全消失。

必须修成：

1. rotation 不得删除仍有 `stopping` 物理 identity 的 tombstone；这些行最多受物理 watch cap 限制，
   必须带新 generation 下自洽的 revision/epoch 保留到 teardown 完成；
2. 对 post-rotation 当前 authority 中合法不存在的 committed section，冻结明确的 absent 语义，建议
   `committed.revision = 0`、`materializationEpoch = 0`，并让 strict codec 只在 entry 缺失且两数均为 0
   时接受；不得接受“entry 缺失 + rotation 前非零数”；
3. `COMMITTED` 的 state、generation 与 committed counters 始终描述同一个当前 authority；
4. teardown fault 持续时，GET/desk 始终有 tombstone + `pendingDisarm` 行，显示 STOPPING/不可用而非消失；
5. fault 解除后按原 id 停止，随后该完成 tombstone 可按正常 rotation 规则清理。

最低判别测试：

- threshold−1 + 健康 STOP：触发 rotation，Rust body 自洽，真实 TypeScript codec 接受，state/GET 已停止；
- threshold−1 + STOP fault：触发 rotation 后 row 仍可见、pending、原 id 可寻址；解除 fault 后 tick 清理；
- 另一 caller 在 COMMITTED 与 stamp 之间 rotation/purge：缺行只能返回冻结的 0/0 absent shape；
- 回退 tombstone preservation 或 absent normalization 时测试必须失败。

### A4. P1：failure 也必须绑定 intent stamp

`retry` 有 generation/revision/epoch stamp，但 `failure` 没有。旧 PERMANENT failure 因此可附着到
STOP 之后的新 START，永久阻止装配。

必须修成：

- failure 只对产生它的 authority generation/revision/materialization epoch 有效；
- STOP、START、policy edit 或 rotation 改变 stamp 后，旧 failure 不得抑制新 intent；
- 旧 physical id 仍在 `stopping` 时不能重复 arm；一旦旧 teardown 完成，新 intent 立即重新 admission；
- 若现实仍是永久失败，可在当前新 stamp 下重新记录，而不是继承旧结论。

判别反例：arm rev1 → SectionNotFound + stop fault → STOP rev2 → admission 恢复 → teardown 完成前
START rev3 → fault 解除。最终必须停止旧 id、以新 id 装配 rev3、清掉 rev1 failure。再加 policy edit
跨 stuck teardown 的同型反例。

### A5. P1：真实批量按钮只能使用一次点击时的 snapshot

单次 `setSectionIntent` 已在调用时捕获 snapshot，但两个真实批量入口仍逐项 `await` 后再次调用它：

- `LiveWatchProvider.startSelected`；
- WatchWorkspace 的 Apply policy。

后续 section 因而捕获前一 response 带回的新 snapshot，仍会覆盖用户点击时没看到的跨 tab 修改。

必须修成：

- 一次 Start selected / Apply policy 手势只捕获一个 immutable basis；
- 本批全部 section 使用该 basis 的 generation 与各自 revision；
- A 处理期间另一个 tab 把 B rev1 改成 rev2，B 请求仍带 rev1并得到 stale，不能覆盖 rev2；
- 第一项触发 rotation 时，后续项仍带点击时旧 generation，按 stale-generation 停止并重读；
- 不同 section 未被外部改变且 generation 未变时仍可顺序成功；不并行制造自竞态。

测试必须点击真实 Start selected 和 Apply policy 按钮，不能再用两次同步 direct method 调用代替。

### A6. P1：mutation 不确定时立即撤销 READY 使用权

当前 PUT transport/codec/refusal 后虽会重读，但 recovery GET 开始时若原状态是 READY，旧 snapshot
继续可绿、可写、可移除。START 已提交但 response 丢失时，旧 tombstone 甚至允许用户删除唯一管理行。

必须修成：

- mutation 发出后，至少对应 section 进入不可提交、不可移除、不可显示旧 green 的 uncertainty；
- response 丢失、codec failure、409/503 等需要重读时，在 recovery GET 完成前不得恢复 READY 使用权；
- START 的 outcome 不确定时，即使旧 snapshot 没有 desired，也要保留该 section 的管理 identity；
- STOP 不确定时旧 green 立即撤下；
- 不自动重放手势；成功 GET 才以新 authority 恢复操作。

最低 held-promise 测试：

1. START 在服务端提交/物化但 response 丢失，recovery GET 永久 hold：行仍在、非绿、active=0、
   remove/mutation 禁止；
2. STOP 已提交但 response 丢失，recovery GET hold：旧 WATCHING 立即消失；
3. recovery GET 成功后恢复当前真实 state，且没有第三次 mutation。

`intentSaved`/管理 identity 还必须保留任何可能仍有物理 watch 的可信行：`policy != null`、
`pendingDisarm` 或 `materialized != null` 任一成立。不能只保留 policy 非空行，否则 STOP fault + 读取失败
仍会隐藏正在 teardown 的 watch。

### A7. P1：CLOSED/ERROR 必须形成全局 response cutoff

当前 `disprove(null)` 只枚举当前 snapshot 已经 running 的 section。若 snapshot 还是 null/PREPARING，
一个关闭前发出的 GET 在关闭后返回 RUNNING，就能重新点亮已关闭 socket 的页面。

必须修成：

- CLOSED/ERROR 记录全局 connection evidence epoch/cutoff，而不是只枚举当时已知的 running rows；
- 在关闭前或关闭时已经 issued 的任何 authority response，都不能在关闭后恢复 green/active；
- socket 非 OPEN 时页面不从 authority snapshot 声称可响铃；
- 只有后续 OPEN 之后新 issued、成功返回的 GET 才能解除全局 cutoff；
- section-specific WATCH_STOPPED disproof 继续按其事件顺序工作。

判别测试：snapshot null 与 PREPARING 各一组，GET/START_RESULT refresh 被 hold → CLOSED/ERROR →
旧 GET 返回 RUNNING，仍必须非绿；随后 OPEN → 新 GET 返回当前 running，才允许恢复绿色。

### A8. P2：Windows policy helper 必须真正精确

当前 helper 会把以下错误对象判成相同：FINITE 600 与 FINITE 600 + extra key、FINITE 600.4、
数字字符串 `"600"`，以及 policy 顶层 extra key；原因是没有精确键集并强制转成 `[long]`。

必须修成：

- policy 精确键集：`notificationMode/maxAudible/continuousDuration`；
- FINITE duration 精确键集：`kind/seconds`；UNLIMITED 精确键集：仅 `kind`；
- maxAudible/seconds 必须是 JSON 整数数值，不接受 float、numeric string、null、bool；
- mode/kind 必须是已知字符串；
- self-check 增加顶层 extra、duration extra、600.4、`"600"`、fractional maxAudible 等反例；
- 真实 final archive 仍跑完整三生命周期门。
