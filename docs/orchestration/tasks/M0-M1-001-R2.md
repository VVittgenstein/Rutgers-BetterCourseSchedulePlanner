### A3. P1：失效复验的 teardown 失败不能丢 activeWatchId

当前复验路径先调用 `disarm()`。`disarm()` 失败时正确保留 `armed`、设置
`pendingDisarm` 与 retry；但调用方随后无条件执行 `state.armed = None`。`DisarmRetry` 本身不保存
watch id，后续 teardown 又都从 `armed` 取 id，因此这一组合会让仍活的物理 watch 永久不可寻址。

必须修成：

- Catalog/term/campus/target 失效触发 teardown，而 owner stop 失败时，保留原 activeWatchId；
- GET 必须显示非绿的 `STOPPING`/失败状态，但仍保留足以寻址真实 watch 的 running identity；
- stamp-safe teardown retry 到期后仍针对原 id，不得误停同 section 后来产生的新 watch；
- 用户随后提交 STOP 也必须能按原 id 停掉它；
- 成功 stop 后再清 id/pending/retry；desired intent 与失效原因按既有合同保留。

最低判别反例：

```text
arm → admission 变 SECTION_NOT_FOUND（另加一个 transient 变体）
→ FaultOwner.stop 失败且物理 watch 仍活
→ 断言 pendingDisarm、非绿、原 activeWatchId 仍可寻址
→ fault 解除 → tick/或用户 STOP → 精确旧 id 被停、owner 空
```

该测试必须能打挂 `c50499f` 的无条件 `state.armed = None`。

### A4. P1：Full Reset 最终 teardown 失败不能返回成功并忘记 watch

当前 `finish_authority_reset()` 对最终 live-set 的 `owner.stop` 错误只记日志，随后仍清空全部
materialization、降低屏障并返回 `Ok(())`；personal surface 还会吞掉 finish 错误。若兜底 teardown
失败，authority 可以已经为空，但活 watch 被彻底隐藏。

必须修成：

- `finish_authority_reset()` 只有在最终 owner live set 为空时才能清记录、降低屏障并成功；
- 任一 teardown 失败时不得同时做到“返回成功 + 丢地址 + owner 仍活”；
- 保留每个失败 target 的 identity，并提供可确定到达的重试/再次 finish 路径；
- personal reset surface 不得吞掉该失败后仍向页面报告成功；
- fault 解除后能完成 cleanup，屏障正常降低，普通 reset 后 socket 仍可继续使用；
- 健康 reset、SQLite clear 失败/忙、既有 blocked-clear 并发反例均不得回归。

最低 fault 反例：在屏障内放入一份 coordinator 无记录的 owner watch，令最终 stop 失败；第一次
finish/HTTP 不能成功，watch id 仍可寻址且 reconcile 不能绕过屏障；解除 fault 后重试，最终
authority/owner/active/materialization 全空，再证明新页面仍能正常使用。

### A5. P1：terminal refusal 必须由同一个 authority snapshot 盖章

当前 terminal outcome 在 store transaction 中按 generation G 决定；`describe()` 另读 generation，
而 `restamp()` 在“本 caller 没有执行 rotation”时提前返回。另一线程若在其间 rotation，响应会把
G 的 `currentRevision` 与 G+1 的 `authorityGeneration` 拼在一起。

必须修成：

- COMMITTED 与所有 terminal refusal 的 generation/revision/epoch 字段都来自一个自洽 authority
  snapshot；不能用“是否由本 caller 旋转”判断是否需要 restamp；
- 并发 rotation 在 outcome 与 response 之间发生时，STALE_REVISION 的 `currentRevision` 必须属于
  返回的 `authorityGeneration`；
- LIMIT_EXCEEDED/STALE_GENERATION/MUTATION_ID_CONFLICT 同样保持各自精确 shape；
- replayed terminal refusal 仍是原 409，不伪造成 200，也不重放手势。

必须增加两个判别测试：

1. terminal receipt 自己跨 threshold 并触发 rotation，完整检查 response，而不是只取 outcome；
2. 用显式 rendezvous 强制“terminal outcome 已决定，另一 caller 先 rotation，随后才组 response”，
   断言 generation/currentRevision 同代且 status 仍为 409。

### A6. P1：串行响应不等于静默 rebase 用户手势

统一 authority 队列是正确方向，但 `submitIntent()` 当前在队列 callback 真正运行时才读取最新
`intentSnapshotRef`。这违反 `WatchIntentPort` 已冻结的合同：提交必须比较用户做手势时看到的 snapshot。

确定反例：rev1 WATCHING；用户点 STOP，响应被 hold；在 STOP 返回前又点 Apply policy。当前实现让
STOP 写 tombstone rev2，再让第二手势静默改用 rev2 提交 START rev3，复活用户刚停止的 watch。

必须修成：

- 手势进入队列时就捕获 generation 与该 section revision（或不可变 snapshot）；
- 队列只负责响应顺序，不能替手势换成用户从未看到的 base；
- 同 section 的后续手势若前一手势已改变状态，必须 STALE/CONFLICT 后只重读，不自动重放；
- 不同 section 在 generation 未变化且各自 revision 未变化时仍可依次正常提交；
- rotation 改变 generation 时，排队中的旧手势按正常 stale-generation 处理。

必须有 deferred-promise 真实反例：`STOP(rev1)` → 未返回时 `policy/START(rev1)` → STOP 提交 rev2 →
第二请求仍携带 rev1 → 409 → 只 GET、不出现第三次 mutation，最终保持 tombstone。

### A7. P1：收到物理反证后立即撤绿，同时保留可管理 identity

当前 `WATCH_STOPPED` 只清旧 socket `active[]` 并排队 GET；local `effectiveActive` 来自仍为 READY 的
旧 authority snapshot。只要后续 GET 延迟或挂起，badge、active count 和连接文案就可无限假绿。
`CLOSED/ERROR` 也有同类问题。另一方面，GET 失败会把 snapshot 整体清成 null，使不在 selection
中的 saved desired row 从 desk 消失。

必须同时满足：

- `WATCH_STOPPED` 是物理 watch 已停止的直接证据；事件处理完成时对应 section 立即不再
  `WATCHING`，不等待 GET；
- local socket `CLOSED/ERROR` 后，当前页面不得继续用旧 materialized snapshot 显示绿色或非零 active；
- 后续 GET 仍进入统一顺序域，成功时恢复当前真相，失败时保持非绿；
- “不信任旧 green”不等于“忘掉管理入口”：最近一次可信读到的 desired-only section identity
  在 LOADING/FAILED 时仍显示为 saved/unavailable 行；
- 非 READY 时不得用旧 revision mutation、不得移除/隐藏该行；成功重读后再恢复 STOP 等操作；
- 不新增 desired WS、实时跨 tab 同步或自动重连。

最低真实渲染测试：

1. 初始 WATCHING → 发 `WATCH_STOPPED` → 把 GET 永久 hold；在 promise 未完成时断言无绿色、active=0；
2. 初始 WATCHING → CLOSED 与 ERROR 各一例；无需 GET 也不再绿色；
3. `selected=[]`、先读到 desired-only running row → 下一次 GET 500；行仍在、显示 unavailable、
   active=0、无 removal/mutation；再成功 GET 后恢复当前控制。

### A8. P1：所有入口必须使用同一五态词义

必须修成：

- 搜索结果入口与 WatchWorkspace 使用同一个状态映射；
- 只有 `intentState === WATCHING` 才显示“监控中”；

增加 `SectionSelectionAction` 真实渲染矩阵：完整四元组匹配、无 materialized、永久失败、
pending disarm、tuple/policy mismatch、LOADING、FAILED。
