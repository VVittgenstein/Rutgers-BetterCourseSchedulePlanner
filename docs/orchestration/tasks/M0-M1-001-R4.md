### A3. P1：rotation 必须按物理 live truth 保留 tombstone

R3 的 `rotate_if_due()` 只从 `materialization.sections[*].stopping` 构造 preserve set。它没有覆盖
“STOP 已经在 SQLite 提交、但尚未取得 materialization lock 做 reconcile”的合法中间态：

1. section 已经物理 armed，receipt/tombstone budget 已到 rotation threshold；
2. rotation 持有 materialization lock；
3. 并发 STOP 在 store 中提交 tombstone，然后阻塞在 reconcile 前；
4. materialization 仍把该 section 记为 `armed`，所以 R3 preserve set 不含它；
5. rotation 删除刚提交的 tombstone；
6. rotation reconcile 尝试 stop，owner stop 恰好失败，于是内部留下 `stopping` id；
7. GET 只投影 authority rows，物理 watch 仍活却再次无 row、无 STOP 控制。

注意：仅把 store guard 从 budget read 持有到 rotation **不能**完整修复，因为 STOP 可以在 rotation
开始前就已经提交、只是在 reconcile 前暂停。

必须修成：

- tombstone 是否仍承担物理 teardown identity，由 owner 的当前 live-watch truth 决定，而不是只看
  materialization 已经来得及切换到哪个标签；
- 推荐在持有 materialization lock 时，从 `owner.watch_targets()` / `live_watches(owner)` 的 section keys
  构造 `preserve_tombstones`，再交给 store rotation；等价方案必须证明覆盖 committed-before-reconcile；
- live snapshot 之后 watch 消失而多保留一条 tombstone是安全的；仍活 watch 被漏掉不是；
- 不得把所有 tombstone 永久保留，也不得扩大 authority 的 9 条 desired cap；
- STOP fault 后必须保留 `policy = null` row、`pendingDisarm = true`、原 physical id 可寻址，且 response
  不能使用“合法已回收”的 absent 0/0 shape；fault 解除后仍按原 id 清理。

最低判别测试必须无 sleep，并建立如下真实顺序：rotation 到 `RotationDue` → 并发 STOP 已完成 store
commit、到 `MutationDecided`/reconcile 前 → rotation 继续 → owner stop fault。当前 `b450ed0` 必须失败；
修复后断言 row 仍在、pending、physical id 仍 live/addressable，随后解除 fault 可完成 teardown。

### A4. P1：mutation uncertainty 的同步权威只能有一个

`markUncertain()` 同步写 `uncertainAt.current`，但生产提交门和 removal 门仍读
`uncertainKeysRef.current`；后者只由 React `useEffect` 在下一轮 render 后同步。`b450ed0` 的提交说明
声称已经改读同步 map，但该提交实际只改测试/文档，没有改 production file。

必须修成：

- 从 PUT 真正发出的同一时刻起，同 section 的第二手势与 remove 都直接读取同步权威；
- 优先让 `submitAgainst` 与 `isRemovable` 直接检查 `uncertainAt.current.has(identity)`，并删除不再需要的
  effect-lagged mirror；等价方案必须在 `markUncertain` 内同步更新唯一门控 ref；
- 不能依赖下一次 render/effect、按钮重渲染或服务端 CAS 才拒绝；
- settle 只能继续由同 sequence 或更晚的成功 authority answer 清除；不能自动重放。

判别测试必须在**同一个 `act` 回调**中：让首个 PUT 已被 fetch mock 观察且保持 pending，不退出 `act`
就立即发第二手势并调用 remove。必须本地拒绝、selection/管理 identity 不消失、PUT 始终只有 1 次；
随后首个 answer/recovery read 落地才恢复操作。现有“第一个 act 完成后再点第二次”的测试保留，但不能替代它。

### A5. P2：只有 OPEN 后的新 GET 可以解除 socket cutoff

R3 A7 冻结的是：CLOSED/ERROR 后，只有 OPEN 之后新 issued 且成功返回的 GET 才能解除全局 cutoff。
当前 `applyAuthority()` 不知道 answer 来源，因而 PUT 的 COMMITTED snapshot 也能解除。

必须修成：

- 给 authority answer 标记证据来源，或只在 `refreshIntent` 的成功 read path 执行 cutoff release；
- mutation response 可以更新 authority snapshot、settle uncertainty，但不得单独恢复 green/active；
- OPEN 本身也不得解除；必须等 OPEN 后的新 GET 成功；
- section-specific disproof 与已有 CLOSED/ERROR × null/PREPARING 四例保持不变。

判别测试：先建立 cutoff；在同一个 `act` 中切到 OPEN，并在 reconnect effect 的 GET 排队前让一个 PUT
返回 RUNNING snapshot。此时仍不得绿色；随后 OPEN 后的新 GET 成功才恢复。回退 evidence-kind 控制时
该测试必须失败。
