## 2. Round 3 起因与 HumanTest 事实

### 2.1 直接观察

状态：`OBSERVED`

用户在 `Z:\Project\Rutgers-BetterCourseSchedulePlanner\HumanTest` 中解压并运行 RC2 最终 Windows 包。包的 provenance 和可执行文件与 RC2 最终提交一致。HumanTest SQLite 记录的关键时间线如下：

| 本地时间（Asia/Shanghai） | 事件 |
|---|---|
| 22:44:11 | 开始 discovery |
| 22:44:27 | discovery 成功，形成 9 个学期 × 15 个 Campus = 135 个组合 |
| 22:44:27–22:45:19 | 前 40 个 Catalog 目标连续成功 |
| 22:45:19 | 开始 `12025/NB`（Spring 2025 / New Brunswick） |
| 22:47:19 | 约 120 秒后失败，被记录为 `CATALOG_UPSTREAM_SCHEMA` |
| 此后 | 未再发起 Catalog 或 Open 请求 |
| 22:52 左右 | 用户退出 HumanTest，终端和浏览器均已关闭 |

前 40 个 Catalog 目标中：

- 18 个返回非空课程数据；
- 22 个返回合法空数组；
- 共取得约 5.58 MB 解码数据和 2,532 个课节；
- 总耗时约 52 秒。

因此：

- SOC Catalog 基础 GET 路径能够工作；
- 截图中的 Open `0/135` 表示 Open 尚未被调用，不是 Open API 已调用并失败；
- 失败后的“正在重试”文案不符合后台事实：前端只继续读取状态，没有触发真正的后端重试；
- 一个目标的失败停止了所有后续目标。

### 2.2 高置信根因判断

状态：`INFERRED`

同一个 `12025/NB` 在 RC2 QA 中于同日多次成功，返回相同内容哈希、约 20.5 MB 解码数据，耗时约 20–54 秒。类似大型 NB 目标也出现过“先成功、后来慢请求被报为 Schema”的现象。因此，稳定的上游字段 Schema 漂移基本可以排除。

与证据最吻合的失败链是：

```text
大型 gzip/body 响应读取或解压过慢
→ 命中 120 秒总超时
→ 底层错误同时带有 decode/timeout 特征
→ 代码先判断 decode，后判断 timeout
→ 被归类为 ContentDecoding / CATALOG_UPSTREAM_SCHEMA
→ 再升级为 FatalProtocol
→ 打开整个 Rutgers origin 的 FatalDiagnostic 熔断
→ 后续 Catalog 与 Open 全部停止
```

该链路不能被写成百分之百还原的 HTTP 现场，因为失败时的 HTTP status、Content-Type、已读取字节数和底层错误链没有完整保留。它是高置信推断，不是直接观察。

本地代理/TUN 路径存在不稳定信号，但它不能单独解释本次事件：同一次运行的前 40 个请求均成功。真正把一次网络抖动放大为整机不可用的，是本方的误分类、全局熔断和全量门禁设计。

### 2.3 问题定性

状态：`ACCEPTED`

SOC API 本身没有突然变得难以使用。RC2 将普通的目标级 JSON 拉取扩张成了：

```text
9 个学期 × 15 个 Campus
→ 135 个 Catalog 串行请求
→ 135 个 Open 串行请求
→ 全部成功且没有 blocking issue
→ 才开放任何搜索
```

这把 135 个独立目标错误地组成了一个不可部分成功的全局事务，并把一个普通慢请求升级成了整个 Rutgers 来源的永久停摆。Round 3 必须修正的是本方架构，而不是给 SOC GET 再增加防御层。

## 3. 总体设计原则

状态：`ACCEPTED`

数据主链恢复为：

```text
取得原始 JSON
→ 解析
→ 规范化
→ 写入数据库
```

约束如下：

1. 拉取必须快速、稳定、可重试，并能容忍普通网络抖动。
2. 每个 `(学期, 真实 Campus)` 独立调度、独立成功、独立失败。
3. 单个目标失败不能阻塞其他目标或整个应用。
4. 不再以全部历史数据完备度决定用户当前选择是否可用。
5. 不以治理、诊断或理论异常为理由损害正常产品功能。
6. 保留解决真实问题所需的最小诊断信息，但不再建立庞大的全局错误状态机。

## 4. 学期范围与时间口径

状态：`ACCEPTED`

### 4.1 当前学期判定

- 使用 `America/New_York` 时区；不得直接使用运行机器的本地时区。
- 使用 Rutgers 实际教学学期，而不是简单采用 SOC 页面默认选择项。
- 学期顺序为 `Winter → Spring → Summer → Fall → 下一年 Winter`。
- 学期间空档归入最近即将开始的学期。
- 例：`2026-07-17` 判定为 Summer 2026；下一学期为 Fall 2026。

### 4.2 Public 范围

- 只显示当前学期和下一学期。
- 两个学期都在启动后自动进入首次完整拉取。
- Public 不提供手动拉取 UI、API 或隐藏能力。
- Public 不允许任意年份、任意历史学期或无限时间范围。

### 4.3 Windows Local 范围

- 固定显示以当前学期为中心的五个学期：前两个、当前、后两个。
- 当前学期和下一学期自动进入首次完整拉取。
- 其余三个尚未拉取的学期以灰色显示，但仍可被选中；选中后允许用户手动拉取。这里的“灰色但可选”是学期选择行为，不得与未 READY Campus 的不可选择状态混淆。
- 不提供自由输入年份、任意历史学期或无限时间范围。
- 窗口外旧数据可以留在数据库中，但不进入普通选择器和自动刷新范围。

## 5. 统一学期选择与单按钮合同

状态：`ACCEPTED`

### 5.1 选择行为

- 学期使用统一的单选方框。
- 用户选中学期只修改选择草稿，不立即清空或切换当前查询范围。
- 查询范围只有在用户显式点击按钮后才切换。

### 5.2 唯一按钮

页面只使用一个主操作按钮，业务文案只允许：

- `拉取`
- `应用`

不允许出现：

- `继续拉取`
- `正在拉取`
- `已应用`
- 其他第三种业务文案

按钮状态按以下优先级求值，避免自动拉取、手动拉取和部分 READY 状态互相覆盖：

1. 如果用户实际选择的全部查询目标均 READY，则按钮为 `应用`；未被选择但仍在后台拉取的 Campus 不影响该结果。
2. 否则，如果这是 Local 中从未请求过的可手动学期，则按钮为 `拉取`。
3. 否则，数据尚未满足应用条件；自动范围显示 disabled `应用`，已由用户触发的 Local 手动范围显示 disabled `拉取`。两者的真实进度均在按钮外呈现。

| 场景 | 按钮 | 行为 |
|---|---|---|
| Local 选择从未请求的可手动学期 | `拉取`，enabled | 启动与默认拉取完全相同的流程 |
| 所选查询目标均 READY | `应用`，enabled | 切换当前查询范围，不发起网络请求 |
| Local 手动范围已开始拉取，但所选目标尚未全部 READY | `拉取`，disabled | 防止重复入队；后台自动继续，进度在按钮外显示 |
| 自动范围中所选目标尚未全部 READY | `应用`，disabled | 后台按真实状态继续拉取/重试 |
| 所选范围已经是当前应用范围 | `应用`，disabled | 由独立标识说明“当前使用” |

手动拉取成功后不得自动应用。用户必须再次显式点击 `应用`。

### 5.3 独立状态区域

拉取阶段、正在处理、写库、等待重试、失败原因和真实进度由独立状态区域承担。按钮不承担进度显示。

UI 只能在后台确实已安排重试时显示“正在重试”。任何“重试”操作都必须调用真实的后端重试入口，不能只刷新状态页面。

## 6. Campus 模型与 `ONLINE_*` 决策

状态：`ACCEPTED`

### 6.1 删除三个线上别名目标

`ONLINE_NB`、`ONLINE_NK`、`ONLINE_CM` 是 NB、NK、CM 的线上/远程课程服务器端筛选范围，不是三个独立 Campus。

已有 Summer、Fall、Winter 真实数据表明：

- `ONLINE_NB` 的课节全部存在于 `NB`；
- `ONLINE_NK` 的课节全部存在于 `NK`；
- `ONLINE_CM` 的课节全部存在于 `CM`；
- 没有发现只存在于 `ONLINE_*` 的独有课节；
- ONLINE 响应内部的真实 `campusCode` 仍是 NB、NK 或 CM；
- Open index 集合同样是对应真实 Campus 集合的子集。

因此，三个 `ONLINE_*` 必须同时从以下位置删除：

- Catalog 拉取目标；
- Open 拉取目标；
- Campus 选择器；
- READY 和进度计数。

线上课程继续归属 NB、NK、CM，并通过现有“授课方式：线上”筛选表达。

### 6.2 目标数量

每学期由原 15 个目标降为 12 个真实 Campus 目标。当前 discovery 返回的范围在排除三个 `ONLINE_*` 后，观察到 12 个代码：

```text
NB, NK, CM, B, CC, H, CU, MC, L, AC, J, D
```

这是一份当前观测清单，不应被实现为永久硬编码 allowlist；生产目标仍由 discovery 得到，再按本记录排除 `ONLINE_*` 别名。

当前学期和下一学期的默认首次范围为 24 个 `(term, campus)` 完整目标单元。这不等于总共只有 24 次 HTTP；每个完整目标至少需要 Catalog 和 Open 两个来源，重试另计。

## 7. READY 粒度、完整快照与原子发布

状态：`ACCEPTED`

### 7.1 READY 的唯一粒度

READY 以 `(学期, 真实 Campus)` 为粒度，不以整个学期、全部 Campus 或全局总数为粒度。

统一标准为：

```text
Catalog 原始 JSON 有效取得并处理成功
AND
对应 Open 有效取得、关联验证并处理成功
AND
Catalog + Open 作为完整快照成功提交
= READY
```

所有真实 Campus 使用同一 READY 标准。NB 的优先级不能改变成功定义。

经过完整性和关联规则判定为有效的空集合可以构成成功结果；不能把所有空响应无条件视为成功，也不能把合法空数组无条件视为 Schema 错误。

### 7.2 搜索门禁

- Catalog-only 和 Open-only 都不是可供查询的完整状态。
- 用户实际选择的每个 `(term, campus)` 都 READY 后，才允许 `应用` 和查询该范围。
- 未被用户选择的失败 Campus 不阻塞已选择的 READY Campus。
- 一个学期可以处于部分可用状态；聚合学期状态不得掩盖 Campus 级真实状态。
- 从未获得完整快照、正在首次拉取或首次重试的 Campus 灰显、不可选择，并显示加载标识。
- 已有完整快照但刷新失败的 Campus 继续可用，不得退回“未拉取”灰色状态。

### 7.3 首次完整发布

每个目标的首次流程为：

```text
GET courses.json
→ 完整读取并验证 JSON
→ 解析与规范化 Catalog
→ 暂存候选 Catalog
→ 获取对应 Open
→ 按候选 Catalog 进行关联验证和处理
→ Catalog + Open 一次性提交
→ 标记 READY
```

任一步失败时，该目标仍没有可见的部分版本；后台只重试该目标。

### 7.4 已有完整数据时的 Catalog 刷新

设当前完整快照为 `Cn + Om`。Catalog 刷新时：

```text
取得并处理 Cn+1
→ 暂存 Cn+1
→ 获取并处理与 Cn+1 匹配的新 Open
→ 两者全部成功
→ 原子替换为 Cn+1 + On+1
```

如果任一步失败：

```text
继续提供 Cn + Om
→ 显示“刷新失败，正在重试”
→ 按目标重试
```

禁止公开新 Catalog 与旧 Open 混合的半套版本。

### 7.5 两次 Catalog 刷新之间的 Open 更新

Catalog 与 Open 共同组成可用快照，但不意味着每次 10 秒或 30 秒的 Open 刷新都重新下载 Catalog。

高频 Open 更新依附当前已提交的 `Cn`：

```text
取得 Om+1
→ 对 Cn 完成关联验证和处理
→ 成功后将完整快照原子更新为 Cn + Om+1
```

如果 Open 获取或关联失败，则继续提供 `Cn + Om` 并按策略重试。系统始终不公开未经当前 Catalog 验证的 Open，也不出现可用的 Catalog-only/Open-only 状态。

## 8. 有界并行、调度与重试

状态：`ACCEPTED`

### 8.1 并行模型

- Catalog/完整目标允许并行拉取；当前初始上限固定为 3 个目标工作流。
- 不建立复杂的自适应并发控制器。
- 网络请求可以有界并行；SQLite 最终发布使用短事务并安全串行，不代表网络必须全局串行。
- 不先积攒整个学期的全部 JSON；每个目标完成后即可独立发布 READY。

### 8.2 目标级故障

以下普通、可恢复故障只影响并自动重试当前目标：

- 连接失败或 timeout；
- 408/常规 5xx；
- gzip/body 读取或解码中断；
- 截断 JSON；
- 可恢复的目标级解析或规范化失败。

timeout 分类必须优先检查，并保留完整错误链；不能再次把慢请求的 decode 包装直接升级为全局致命 Schema 故障。

确定性的 Schema/规范化合同错误也必须隔离在当前目标，不得封锁 origin；它应保留诊断并按有界退避重新获取后再处理，不能对同一失败 payload 形成 CPU 紧循环。精确恢复策略由实现计划依据错误是否可恢复来确定。

只有明确的 `429/Retry-After` 等来源级限流信号，才能暂停对 Rutgers origin 发起新的请求。暂停到期后应恢复，不得进入生产环境中无法解除的永久熔断。

### 8.3 优先级与退避

- 调度与重试强度支持按 Campus 配置；NB 是最高优先级目标，采用更积极的重试策略。
- 在应用仍运行时，NB 不应因普通瞬态故障被永久放弃。
- “持续重试”必须包含退避和上限间隔，不能形成紧密循环或持续轰炸上游。
- 其他 Campus 的精确权重与重试强度尚未冻结，但 READY 标准完全相同。
- 用户当前显式发起的本地手动拉取应进入同一队列和流程，并获得交互请求优先级；不得另建第二套实现。

精确退避秒数、其他 Campus 的具体权重和解析 worker 数属于后续实现计划参数；本记录不捏造尚未冻结的数字。

### 8.4 最小诊断

失败记录至少应保留可用于真实定位的脱敏信息：目标、阶段、HTTP status（若取得）、Content-Type、已读取字节数、错误类别、完整底层错误链摘要和 trace ID。诊断用于解释和恢复，不驱动不成比例的全局状态机。

## 9. 刷新时钟与范围调度

状态：`ACCEPTED`

### 9.1 基线频率

| 数据/场景 | Public | Windows Local |
|---|---|---|
| Catalog 普通刷新 | 固定 10 分钟 | 默认 10 分钟；可配置 1–1440 分钟 |
| Open 普通刷新 | 固定 30 秒 | 默认 30 秒；可配置 3–3600 秒 |
| Watch Fast Lane | 固定 10 秒 | 默认 10 秒；可配置 3–60 秒 |

`6 小时`不是 Catalog 刷新周期。它曾用于 discovery generation/学期与 Campus 元数据的低频重新发现，不得写入 Round 3 的课程数据刷新合同。

### 9.2 当前应用范围

当前应用学期内、实际进入查询范围的 Campus 目标使用：

- Catalog 普通刷新时钟；
- Open 普通刷新时钟。

默认即 Catalog 10 分钟、Open 30 秒；Local 使用用户合法配置值。

### 9.3 Fast Lane

Fast Lane 跟随真实 active watch 的 `(term, campus)`，不跟随当前搜索页面。

- 某目标只要存在 active watch，就进入 Watch Fast Lane；
- 即使该学期不是当前应用查询范围，active watch 仍保持 Fast Lane；
- Fast Lane 只覆盖实际存在监看的目标，不提升整个学期或全部 Campus；
- 未应用且没有 active watch 的目标不进入 Fast Lane；
- Fast Lane 只提高 Open 频率，不提高 Catalog 频率。

Local 实际监看 Open 间隔为：

```text
min(普通 Open 配置, Watch Fast Lane 配置)
```

例如普通 Open 为 3 秒、Fast Lane 为 10 秒时，监看目标继续使用 3 秒，不能因进入 Fast Lane 反而降速。

### 9.4 非应用、非监看范围

以下是“当前应用范围走普通时钟、active watch 走 Fast Lane、其他范围低频或不自动刷新”这一已接受原则的直接调度规则；低优先级维护的精确周期尚未冻结。

- 当前学期和下一学期仍完成默认首次完整拉取。
- 下一学期在未应用、未监看时只属于低优先级维护范围，不进入普通或 Fast Lane 高频循环。
- Local 手动拉取的另外三个学期完成首次拉取后，在未应用、未监看时默认不自动周期刷新。
- Local 手动学期被应用后，进入普通 Catalog/Open 时钟。
- “低优先级维护”的精确周期可在实现计划中结合真实负载确定，但不得等同于当前应用范围的 10 分钟/30 秒，也不得进入 Fast Lane。
